# 轻量对比测试模板

这个模板用于搭建“多阶段、多方案、强调结果归档与过程接手”的轻量对比测试项目。

它适合:

- 以素材、文档、提示词或测试结果为主要资产的项目
- 需要横向对比多个方案的测试型项目
- 需要轻量治理骨架, 但暂时不需要 CLI 模板能力的项目

## 轻量特征

这里的“轻量”指的是结构减法, 不是能力不足。

这类模板通常有以下特征:

- 根目录尽量保持简洁干净
- 业务目录直接暴露, 方便人工阅读和维护
- 治理信息集中在 `.agents/`
- `docs/` 负责结构、索引和说明
- `prompts/` 与阶段目录直接承接业务事实

它追求的是“根目录就能直接看懂项目”, 而不是先铺一层重型适配输出再开始工作。

## 推荐目录骨架

推荐保留以下 4 层主体结构:

1. 公共输入层
2. 提示词层
3. 阶段执行层
4. 治理层

### 最小人工根结构

推荐把根目录收敛到这类最小人工结构:

```text
.
|-- .agents/
|-- 00-公共资源/
|-- 01-第一阶段-线稿/
|-- 02-第二阶段-上色/
|-- 03-第三阶段-动作/
|-- docs/
|-- prompts/
`-- README.md
```

这里不把 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md` 视为轻量模板的人工维护必需项。

如果项目后续引入 `vibe-governance` 或其他生成式治理工具, 才可能出现这类 agent 入口文件。

### 主体业务结构

推荐目录骨架:

```text
.
|-- 00-公共资源/
|-- prompts/
|-- 01-第一阶段-线稿/
|-- 02-第二阶段-上色/
|-- 03-第三阶段-动作/
|-- .agents/
`-- docs/
```

说明:

- `00-公共资源/` 用于放公共素材、人物资料、体裁定义和原始输入
- `prompts/` 用于放阶段0到阶段3的提示词与节点定义
- `01/02/03` 目录用于承载各阶段测试执行、输出结果和记录沉淀
- `.agents/` 用于放规则、接手信息和过程记录
- `docs/` 用于放结构说明、索引和目录视图

### `.agents/` 最小治理骨架

如果这个模板要承接 Taotaotao 这类“可接手、可追溯、可沉淀”的治理闭环, 不能只带一个空的 `.agents/` 目录名。

至少要把下面这组最小治理骨架一起带上:

```text
.agents/
|-- README_中文.md
|-- profile.yaml
|-- RULES.md
|-- architecture-decisions.yaml
|-- overrides/
|   |-- README_中文.md
|   `-- rules.yaml
|-- PROGRESS.md
`-- progress/
    |-- README_中文.md
    |-- ENTRY_TEMPLATE.md
    `-- entries/
        |-- README_中文.md
        `-- YYYY/
```

其中:

- `.agents/profile.yaml` 用于固定项目画像与治理配置
- `.agents/architecture-decisions.yaml` 用于沉淀稳定架构决策
- `.agents/overrides/rules.yaml` 用于放本地规则 override
- `.agents/PROGRESS.md` 是滑动索引, 用于承接当前活跃进展
- `.agents/progress/ENTRY_TEMPLATE.md` 是新增 progress 条目的统一模板
- `.agents/progress/entries/YYYY/` 用于按年份沉淀原始条目
- `.agents/progress/entries/README_中文.md` 用于说明条目目录的职责和组织方式

如果缺少 `profile.yaml`、`overrides/rules.yaml` 或 `progress/entries/` 这些关键层, 说明引入的还只是“轻量目录结构”, 不是完整的治理记忆闭环。

## 可选的最小多 agent 入口层

如果项目希望保留多 agent 协作入口, 但仍然不引入多 IDE 扩展层, 可以只保留这组最小根级入口:

- `AGENTS.md`
- `CLAUDE.md`
- `GEMINI.md`

要特别区分:

- 这组文件属于“多 agent 最小适配层”
- `.cursor/`、`.github/`、`.opencode/` 属于“多 IDE 扩展层”
- 前者可以单独存在, 不等于后者必须一起引入

在 `Taotaotao` 仓里, 这类入口文件通常由 `render` 生成。
在一般轻量项目里, 如果没有引入生成式治理工具, 也可以手工维护, 但要与 `.agents/` 真源保持一致。

## 默认不带的重型部件

下面这些目录默认不是轻量对比测试模板的组成部分:

- `.cursor/`
- `.github/`
- `.opencode/`
- 其他多 IDE 统一适配输出目录

它们不是错误项, 也不是禁止项, 但默认不带。

对这类模板来说, 它们属于扩展层; 只有项目确实需要多 IDE 统一适配时, 再考虑引入。

## 必须保留的稳定规则

### 1. 测试记录规则

- 每一轮测试只保留一个 `第xx轮-测试记录.md`
- 同一文件内按需分段记录 `基本信息`、`归档文件`、`问题总结`、`阶段结论`
- 不再为同一轮拆分独立的 `问题总结` 与 `阶段结论` 文件

### 2. 命名规则

- 方案目录统一使用 `方案xx-名称`
- 轮次目录统一使用 `第01轮`、`第02轮`
- 输出图命名必须能够回溯到方案、轮次、模型与序号
- 图片复制或移动进仓库后, 应按经过的流程方案重命名

### 3. 文档同步规则

只要目录名、提示词名、方案名发生变化, 必须同步更新以下四个真源:

- `docs/信息索引.md`
- `docs/文件结构定义.md`
- `docs/项目目录树.md`
- `.agents/PROGRESS.md`

### 4. bug / 异常触发记录规则

模板里的“自动记录”默认按“触发即记”理解, 即事件一发生就必须落到稳定位置, 即便当前还是人工执行。

- 用户提出 bug、回归、行为异常、规则冲突时, 必须记录
- 如果当前存在具体测试轮次, 先落到该轮 `第xx轮-测试记录.md` 的 `问题总结`
- 如果该问题会影响后续接手、规则判断或结构决策, 再补一条 `.agents/progress/entries/YYYY/` 条目
- 如果没有对应轮次上下文, 至少补一条 progress entry
- 新增 entry 后应运行 `render`, 让 `.agents/PROGRESS.md` 同步更新

### 5. 关键操作留痕规则

- 运行 `render`、`validate`
- 目录结构迁移
- 批量改名或批量移动
- 模板引入、模板升级
- 会影响后续协作判断的规则调整

以上操作默认都属于“必须留痕”的治理事件。

- 原始记录应落到 `.agents/progress/entries/YYYY/`
- `.agents/PROGRESS.md` 只作为滑动索引, 不单独承担完整流水账
- 如果操作直接影响某一轮测试结论, 还应同步更新对应轮次记录

### 6. 阶段0预处理归属规则

- 与结构拆解、约束提取、标准化强相关的预处理内容, 优先归到 `prompts/00-阶段0-原始元素处理/结构提取/`
- 与质量优化、背景处理、裁剪清理、图像修复强相关的预处理内容, 优先归到 `prompts/00-阶段0-原始元素处理/图像预处理/`
- 如果某类中间产物的作用是“从原始输入中剥离出后续流程所需的核心结构”, 应使用项目内统一的中性命名, 不要绑定某个具体业务题材
- 原始输入到中间产物的命名语义应在项目内保持一致, 例如统一采用“源输入 -> 结构化中间产物”的表达方式

## 半抽象模板落法

这个模板不追求彻底抽象成无行业特征的空骨架, 也不建议一比一复制成只服务原项目的专用仓。

推荐采用“半抽象模板”:

- 保留阶段化结构
- 不强制重命名目录
- `线稿 / 上色 / 动作` 可以保留为默认示例阶段名
- 在说明文档中明确: 新项目可按自己的目标图类型替换阶段含义
- `.agents/` 只保留稳定治理逻辑, 不带入原项目的具体历史判断
- `PROGRESS.md` 只保留仍然重要的滑动索引
- `progress/entries/YYYY/` 需要从一开始就建好, 否则后续经验沉淀会失去稳定落点

核心原则是:

- 复制目录结构、规则和说明模板
- 不复制当前测试轮的具体结论
- 不复制当前角色的具体样例
- 不复制只对当前测试阶段成立的临时判断

## 何时保持轻量, 何时加层

判断时只问一个问题:

- 是否需要多 IDE 统一适配?
  - 否: 保持当前轻量结构
  - 是: 再考虑引入更重的适配层或治理层

## 3 个示范锚点

### 锚点 1: 单文件测试记录优于拆文件

- 决策: 每轮只保留一个 `第xx轮-测试记录.md`
- 原因: 能减少重复表述, 降低维护成本, 回看时也更顺

### 锚点 2: 目录变更必须同步四个真源

- 决策: 目录名、提示词名、方案名变化后, 必须同步更新索引、结构定义、目录树和进度索引
- 原因: 真实目录一旦变化而文档不同步, 后续接手会迅速失真

### 锚点 3: 通用预处理能力应集中到阶段0功能子目录

- 决策: 与质量优化、背景处理、裁剪清理、图像修复相关的通用预处理能力, 统一归到 `prompts/00-阶段0-原始元素处理/图像预处理/`
- 原因: 这类节点本质上是正式测试前的公共预处理能力, 集中管理后比散落在业务阶段目录里更稳定

## 不迁移的内容边界

这个模板明确不迁移:

- 具体测试输出图
- 具体轮次问题结论
- 当前角色绑定样例
- 临时操作原文
- 仅对原项目成立的个别测试上下文

换句话说, 这个模板保留的是“方法”和“稳定规则”, 不是原项目案例。
